## Deferred from: code review of story 3-0-1 (2026-04-30)

### Story 3.0.1 — Core Journey E2E Tests (P0-022, P0-023, P2-011)

- **`getByText` substring matching → latent strict-mode trap** — [apps/web/e2e/journey-2-returning-session.spec.ts:54-56](../../apps/web/e2e/journey-2-returning-session.spec.ts#L54-L56), [apps/web/e2e/journey-2-returning-session.spec.ts:80-82](../../apps/web/e2e/journey-2-returning-session.spec.ts#L80-L82). Default `getByText(text)` matches by substring, not equality. Today the per-test `randomUUID()` suffix makes collisions cryptographically negligible, so the tests pass deterministically. If Playwright strict-mode is later enabled (e.g., to catch ambiguity in future specs), or a future spec assertion wraps `toHaveCount(1)`, an accidental substring overlap would surface as a strict-mode violation. Tighten with `{ exact: true }` on `getByText` calls during the same hardening pass that fixes the canary's substring deferral from Story 3.0.
- **Journey 1 captures the server `id` via post-hoc `GET /todos` filter — races optimistic POST reconcile** — [apps/web/e2e/journey-1-happy-path.spec.ts:60-72](../../apps/web/e2e/journey-1-happy-path.spec.ts#L60-L72). The DOM does not expose the server id (no `data-id` on `todo-item` per [TodoItem.tsx:34](../../apps/web/src/components/TodoItem.tsx#L34)), so cleanup uses `GET /todos` + filter-by-text. By the time the GET runs, the test has already asserted `data-completed='true'` (which auto-retries until reconcile completes — handleToggle bails if `pending===true`), so the row IS in the DB and the GET WILL find it — empirically all 3 browsers pass in 1-2s. But under a hostile dev DB scenario (concurrent test deleting our row, or a network blip on the GET) the cleanup gracefully fails open: `createdId` stays `null`, the `afterEach` runs no DELETE, and the row leaks. Mitigation: capture the id via `page.waitForResponse` on the POST /todos response when the create fires through the UI — caches the id at the moment of creation rather than re-discovering it. Bundle into the same hardening pass as the afterEach try/finally items below.
- **`afterEach` DELETE rejection or sequential-loop failure leaks rows** — [apps/web/e2e/journey-1-happy-path.spec.ts:12-21](../../apps/web/e2e/journey-1-happy-path.spec.ts#L12-L21), [apps/web/e2e/journey-2-returning-session.spec.ts:13-22](../../apps/web/e2e/journey-2-returning-session.spec.ts#L13-L22). Same pattern as the canary's existing Story 3.0 deferral (item 1: "afterEach DELETE rejection leaves `createdId` stale"). Journey 1: a thrown rejection (network error, ECONNRESET) skips the `createdId = null` reset — no observable effect today (each test is a fresh instance) but inconsistent with try/finally hygiene. Journey 2: the sequential cleanup loop aborts on the first thrown rejection, leaving up to 2 of 3 rows orphaned. Wrap each iteration in `try { ... } catch (e) { console.warn(...) } finally { ... }` so transient failures don't abort cleanup of remaining ids. Bundle with the canary fix as a single E2E robustness pass when Story 3.6 lands.
- **Unchecked `(await res.json()) as { id: string }` cast in seed loop** — [apps/web/e2e/journey-2-returning-session.spec.ts:46-47](../../apps/web/e2e/journey-2-returning-session.spec.ts#L46-L47). Three iterations of the unchecked cast (vs the canary's one). If POST /todos contract drifts (envelope wrapper, renamed field), `created.id` is `undefined` for each seed, the literal string "undefined" lands in `seededIds`, and cleanup hits `/todos/undefined` — which the API rejects with 400 (Zod UUID validation), not 404. The current `expect([204, 404]).toContain(...)` would FAIL on 400 (whereas the canary's single `as { id: string }` cast was masked by 404 tolerance). Story 2.1's integration tests pin the response shape so drift is caught upstream, but defense-in-depth would be a one-line runtime check — `if (typeof created?.id !== 'string') throw new Error('seed missing id')`. Fold into the same hardening pass.
- **`waitForResponse` predicate could match unintended DELETEs in future specs** — [apps/web/e2e/journey-2-returning-session.spec.ts:67-73](../../apps/web/e2e/journey-2-returning-session.spec.ts#L67-L73). Predicate `r.request().method() === 'DELETE' && r.url().includes('/todos/') && r.status() === 204` is correct for this single-test describe (only one UI delete fires through the page). If a future expansion adds a second UI delete in the same test, the predicate could resolve on the wrong response. Defensive tightening: `r.url().endsWith('/todos/' + seededIds[2])` and accept `[204, 404]` (so an unexpected 404 fails fast with a clear status rather than hanging to 30s test timeout). Apply when the next UI-delete test in this file lands.
- **README "Tagging convention" section not updated to enumerate `@Journey1` / `@Journey2` / `@P2-011`** — [apps/web/e2e/README.md:46-50](../../apps/web/e2e/README.md#L46-L50). Spec AC #5 reads "the README mentions all three" — satisfied via the "Where the tests live" inventory — but tagging convention enumeration would help future contributors discover the per-scenario tags. Sweep alongside Story 3.0.2 / 3.0.3 README updates, which will introduce additional tags (`@A11y`, `@Keyboard`, etc.).
- **README "≤2 added lines" budget exceeded for documentation coherence** — [apps/web/e2e/README.md:38-67](../../apps/web/e2e/README.md#L38-L67). Spec Tasks line constrained the README change to ≤2 added lines; the implementation added ~3 net lines across two sections.
