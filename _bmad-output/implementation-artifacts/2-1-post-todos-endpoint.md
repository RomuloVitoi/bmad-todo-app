# Story 2.1: POST /todos endpoint

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As an API consumer,
I want to POST a JSON body with a todo text and receive back a complete todo entity,
So that clients can create new todos in the shared list (FR23, FR5, FR6, FR7).

## Acceptance Criteria

1. **Given** `POST /todos` with body `{ "text": "buy milk" }`,
   **When** a client issues the request,
   **Then** the response is `201` with a body matching `TodoSchema` — `{ id: <uuid>, text: "buy milk", completed: false, createdAt: <iso-8601> }`,
   **And** the `id` is newly generated by Postgres (`gen_random_uuid()`, different on every call),
   **And** the `createdAt` is server-assigned (not trustable from client input).

2. **Given** `POST /todos` with body `{ "text": "  buy milk  " }`,
   **When** a client issues the request,
   **Then** the stored row's `text` is `"buy milk"` (trimmed by the Zod schema's `.trim()` transform — handler does not duplicate the trim).

3. **Given** `POST /todos` with body `{ "text": "" }` (empty), `{ "text": "   " }` (whitespace-only), or `{ "text": "x".repeat(501) }` (501+ chars),
   **When** a client issues the request,
   **Then** the response is `400` with the Fastify-sensible validation envelope `{ statusCode: 400, error: "Bad Request", message: "<details>" }`,
   **And** no row is inserted into the `todos` table.

4. **Given** `POST /todos` with a body that has the correct shape PLUS unknown fields (e.g., `{ "text": "x", "completed": true }` or `{ "text": "x", "id": "..." }`),
   **When** a client issues the request,
   **Then** the response is `400` because `CreateTodoRequestSchema` is `.strict()` (rejects unknown keys),
   **And** no row is inserted.

5. **Given** `POST /todos` with a body larger than 4 KB,
   **When** a client issues the request,
   **Then** the response is `413 Payload Too Large` (Fastify `bodyLimit: 4096` enforcement, configured in [apps/api/src/server.ts](../../apps/api/src/server.ts) per NFR18),
   **And** no row is inserted.

6. **Given** the API is running with `/docs` enabled (`NODE_ENV !== 'production'` or `ENABLE_DOCS === 'true'`),
   **When** a developer inspects the OpenAPI spec at `/docs/json` (or the UI at `/docs`),
   **Then** `POST /todos` is documented under the `todos` tag with request body schema (`CreateTodoRequestSchema`) and 201 response schema (`TodoSchema`) derived automatically by `jsonSchemaTransform` from `fastify-type-provider-zod`.

7. **Given** [apps/api/test/integration/todos.int.test.ts](../../apps/api/test/integration/todos.int.test.ts),
   **When** the integration suite runs (`npm run test:integration --workspace apps/api` against a live local Postgres),
   **Then** new test cases cover ACs 1–4 (happy path, trim, empty rejection, max-length rejection, whitespace-only rejection, unknown-field rejection) AND verify the inserted row is queryable via a follow-up `GET /todos`,
   **And** all assertions pass.

    import type { CreateTodoRequest, Todo } from '@todo-app/shared';
    // ...existing imports...

    export const createTodo = async (input: CreateTodoRequest): Promise<Todo> => {
      const [row] = await db.insert(todos).values({ text: input.text }).returning();
      if (!row) {
        // `.returning()` always emits the inserted row(s) on Postgres; this is a
        // type-narrowing guard for TS, not a runtime expectation.
        throw new Error('createTodo: insert returned no rows');
      }
      return toWire(row);
    };

  - [x] **Why the existing `toWire` helper** — guarantees the wire shape matches `TodoSchema` (camelCase `createdAt`, ISO-8601 string). The same helper is used by `listTodos`; reusing it keeps GET and POST byte-identical for any given row.

## Dev Notes

### Where this story sits

Story 2.1 opens Epic 2 (Todo Core Loop). It's the smallest possible vertical: just the API endpoint that creates one row. Web-side wiring (the `TodoInput` form, the optimistic reducer actions, the `api.createTodo()` client wrapper) lands in **Stories 2.4 and 2.5**. The endpoint must work end-to-end (DB insert, response shape, validation) before any of those can be built.

After this story:

- `POST /todos` returns 201 with the bare entity per architecture's "Single resource (create)" contract.
- The `todos` table grows by one row per request; `id` and `created_at` are server-generated.
- Swagger UI at `/docs` documents both GET and POST.

This story does NOT touch:

- The web app (Story 2.5 owns the form and the API client wrapper).
- Reducer actions (Story 2.4 adds `addOptimistic` / `addReconcile` / `addFailed`).
- Toast UI on failure (Story 3.2 owns mutation-failure toasts).
- Input preservation on add failure (Story 3.3 owns FR19).

### Critical architectural guardrails

1. **The schemas already exist.** [packages/shared/src/contracts.ts:14-18](../../packages/shared/src/contracts.ts#L14-L18) defines `CreateTodoRequestSchema`. Do NOT redefine, extend with `.strict()` again, or copy into `apps/api/`. Import from `@todo-app/shared`. Story 1.2 closed this contract; reopening it is out-of-scope.

2. **The DB schema and migration already exist.** [apps/api/src/db/schema.ts](../../apps/api/src/db/schema.ts) declares the four columns; the initial migration at [apps/api/drizzle/0000_*](../../apps/api/drizzle/) (Story 1.4) provisioned the table. **No migration is needed for this story.** If you find yourself running `drizzle-kit generate`, stop — you're doing too much.

3. **No SQL `CHECK` constraint on `text`.** Validation is at the API boundary (Zod), not in the database. The architecture explicitly states this: *"Validation: Zod on every request body/params."* ([architecture.md:215](../../_bmad-output/planning-artifacts/architecture.md#L215)). The DB column is `text NOT NULL`, unbounded.

4. **No client-supplied `id` or `createdAt`.** Even though the DB columns have `DEFAULT gen_random_uuid()` / `DEFAULT now()`, a client could try to send `{ text, id, createdAt }`. AC #4 covers this: `.strict()` rejects unknown keys with 400. Do not "be permissive and ignore unknown fields" — that violates the schema and AC #4.

5. **No try/catch in the handler.** Architecture: *"Validation errors: produced by Fastify's Zod integration automatically; do not wrap or re-throw."* ([architecture.md:401](../../_bmad-output/planning-artifacts/architecture.md#L401)). The global `setErrorHandler` (Story 1.5, [apps/api/src/app.ts](../../apps/api/src/app.ts)) catches anything that escapes the handler and logs+returns the sensible envelope. The handler stays a single `await` away from a return.

6. **Single transaction is implicit.** A single `INSERT ... RETURNING` is atomic by Postgres semantics. Do NOT wrap in `db.transaction(...)` — the architecture flags multi-statement transactions as something to add only when there's a multi-row write. Story 2.1 is single-row.

7. **No retries, no backoff.** Architecture: *"No automatic retries in v1. On failure the UI surfaces a toast; the user retries by repeating the action."* ([architecture.md:418](../../_bmad-output/planning-artifacts/architecture.md#L418)). The server just throws on DB error; the user-facing retry is Story 3.x's domain.

### Why this story doesn't need a `Location` header

REST purists might expect `201 Created` to include a `Location: /todos/<new-id>` header. The architecture intentionally omits it because:

- The created entity is in the response body (no need to GET it separately).
- v1 has no `GET /todos/:id` endpoint — there's nothing to point Location AT.
- Adding it later is a non-breaking, additive change.

If you find yourself wiring a `Location` header, stop and check this section. Don't add it.

### POST plugin order — already correct

Plugin registration order in [apps/api/src/app.ts](../../apps/api/src/app.ts) (Story 1.5) places `setValidatorCompiler`/`setSerializerCompiler` BEFORE `swagger` BEFORE `todosRoutes`. Adding the POST handler to the existing `todosRoutes` plugin slots in at the same position — no order changes are needed. Specifically:

- The Zod type provider's compilers must be set before the route's `body`/`response` schemas are compiled. ✓
- Swagger's `onRoute` hook walks routes registered AFTER it. ✓
- The DB plugin (`db`) is registered before `todosRoutes` so `app.db` is decorated by the time the route handler imports `defaultCreateTodo`. **However**, `createTodo` is imported as a module-level function (not via `app.db`), so plugin ordering for the DB decoration is irrelevant for THIS story. The pool is module-singleton ([db/client.ts:11](../../apps/api/src/db/client.ts#L11)).

### Logging — already automatic

Pino logging emits two structured lines per request (Story 1.5): `incoming request` and `request completed`. Both lines carry `requestId`, `method`, `path`, `statusCode`, `durationMs`. POST /todos requires zero handler-level logging beyond what the framework already produces.

If a POST fails with a 500 (DB unreachable, etc.), Story 1.5's `setErrorHandler` already logs at `error` level with the full stack and `requestId`. Don't add `req.log.error(...)` inside the handler.

**Architecture rule on logging user content:** *"Todo text is user content but not private in v1; still, don't log full text at `info` level — log `todoId` at `info`, full text only at `debug`."* ([architecture.md:394](../../_bmad-output/planning-artifacts/architecture.md#L394)). The framework logs request metadata only — not body content — so this rule is satisfied automatically. Do NOT add `req.log.info({ text: req.body.text }, 'creating todo')` or similar.

### Why the integration test goes in `todos.int.test.ts`, not a new file

The architecture's structure pattern says: *"API integration tests: under `apps/api/test/integration/` — they own a different lifecycle (DB setup/teardown)."* ([architecture.md:352](../../_bmad-output/planning-artifacts/architecture.md#L352)). The existing `todos.int.test.ts` file is the natural home for *all* `/todos` endpoint tests — splitting GET/POST into separate files would force each to re-spin `buildTestApp()` and re-run `before`/`after` hooks for marginal organizational benefit. Add POST cases at the end of the existing file.

If/when the file exceeds ~500 lines (after PATCH and DELETE land in 2.2 and 2.3), it's reasonable to split. v1 stays unified.
